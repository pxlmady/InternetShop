# ПР №1 — шпаргалка до захисту (InternetShop)

> Простими словами: що зроблено, як це влаштовано і що відповідати. Факти ті самі, що й у звіті `ПР1_звіт.docx`.

---

## 1. Про що робота — за 30 секунд

- **Тема:** чиста архітектура + Domain-Driven Design (DDD).
- **Що зробили:** вебзастосунок «інтернет-магазин» на **Java 21** (IntelliJ IDEA), без Spring і без сторонніх бібліотек.
- **Шари:** 4 модулі Maven — **Domain → Application → Infrastructure → WebApi** (+ модуль перевірок `internetshop-checks`).
- **Bounded contexts:** **Catalog** (товари) і **Ordering** (замовлення). Спілкуються лише через інтерфейс `ProductCatalog`.
- **Бізнес-правила** живуть тільки в Domain (у Value Objects і в `Order`).
- **Перевірка:** `mvn verify` → `All 51 checks passed.` + `BUILD SUCCESS`.

Одне речення для викладача:
*«Я зробив інтернет-магазин із двома bounded context — Catalog і Ordering; код поділено на чотири шари-модулі Maven, домен не залежить ні від чого, а шари й контексти спілкуються через інтерфейси.»*

## 2. Що вміє застосунок

| Можливість | Як це виглядає |
|---|---|
| Переглянути каталог | `GET /products` або таблиця на сторінці |
| Додати товар | `POST /products` — назва, опис, ціна |
| Видалити товар | `DELETE /products/{id}` → 204 |
| Створити замовлення (чернетку) | `POST /orders` з `customerId` → 201, статус `DRAFT` |
| Додати товар у замовлення | `POST /orders/{id}/items` — `productId`, `quantity` |
| Оформити замовлення | `POST /orders/{id}/place` → статус `PLACED` |
| Переглянути замовлення | `GET /orders`, `GET /orders/{id}` |

При першому запуску в каталозі вже є 3 товари: «Ноутбук 14"», «Бездротова миша», «USB-C кабель».
Дані зберігаються у файлах `data/products.db` і `data/orders.db` і нікуди не зникають після перезапуску.

**Правила (їх перевіряє Domain):**

- назва товару — 1–120 символів, опис — до 1000 символів, ціна > 0;
- кількість одного товару — від 1 до 99 (повторне додавання **сумує** кількість, і сума теж ≤ 99);
- змінювати можна тільки замовлення в статусі `DRAFT`;
- порожнє замовлення оформити не можна, двічі оформити — теж;
- сума грошей — не більше 1 000 000 000, максимум 2 знаки після коми.

## 4. Шари — хто за що відповідає

| Шар | Роль простими словами | Від кого залежить |
|---|---|---|
| **Domain** | «Мозок»: що таке товар, замовлення, які правила | ні від кого (тільки JDK) |
| **Application** | «Диспетчер»: виконує сценарії крок за кроком, правил не вирішує | Domain |
| **Infrastructure** | «Руки»: зберігає у файли, перекладає між контекстами | Application, Domain |
| **WebApi** | «Двері»: приймає HTTP, віддає JSON, збирає все докупи | усі три |

**Головне правило:** залежності тільки **всередину** (до Domain). Domain нічого не знає ні про файли, ні про HTTP.
Це гарантує Maven: якщо модуль не прописав залежність у своєму `pom.xml`, він просто **не скомпілюється**.

**Інверсія залежностей (важливо пояснити!):**
Application *викликає* збереження, але **не залежить** від Infrastructure. Як? Інтерфейс `OrderStore` лежить в Application,
а Infrastructure його *реалізує* (`FileOrderStore implements OrderStore`). Тобто стрілка залежності йде Infrastructure → Application.

**Composition Root** — `InternetShopApp.start(...)`. Єдине місце, де написано, яка реалізація підставляється під який інтерфейс
(DI-контейнера немає, все через конструктори):

```java
ProductStore productStore = new FileProductStore(dataDirectory);
OrderStore orderStore = new FileOrderStore(dataDirectory);
CatalogService catalog = new CatalogService(productStore);
ProductCatalog productCatalog = new CatalogProductAdapter(catalog);
OrderService orders = new OrderService(orderStore, productCatalog);
```

## 5. DDD у проєкті — де саме

| Поняття | Простими словами | У проєкті |
|---|---|---|
| **Entity** | Має Id; той самий Id = той самий об'єкт | `Product`, `Order`, `OrderLine` (базовий клас `Entity`) |
| **Value Object** | Без Id, важливе лише значення, незмінний | `Money`, `ProductName`, `Quantity`, `CustomerId` — Java `record` |
| **Aggregate** | Група об'єктів, яка змінюється як одне ціле | `Order` + його `OrderLine` |
| **Aggregate Root** | Єдині «вхідні двері» агрегату | `Order`: `addItem()`, `place()` |
| **Інваріант** | Правило, яке завжди має бути правдою | ≤ 99 шт., зміни лише в `DRAFT`, не оформлювати порожнє |
| **Bounded Context** | Межа, в якій слова мають одне значення | `catalog` і `ordering` (пакети в Domain і Application) |
| **Repository** (тут Store) | «Колекція» агрегатів, ховає, як зберігаємо | `ProductStore`, `OrderStore` |
| **Application Service** | Керує сценарієм, не вирішує правил | `CatalogService`, `OrderService` |
| **Anti-Corruption Layer** | Перекладач між контекстами | `CatalogProductAdapter` |
| **Shared Kernel** | Маленька спільна частина моделі | `Money`, `Entity`, `DomainRuleException` |

**Як захищено агрегат `Order`:**

- `getLines()` повертає список **тільки для читання**;
- `OrderLine.increase()` і конструктор `OrderLine` видно лише всередині пакета `ordering`;
- усі перевірки — **до** зміни стану, тож при помилці замовлення лишається як було.

**Чому Value Objects — `record`:** перевірка в конструкторі → неправильний об'єкт створити неможливо → не треба перевіряти ще раз деінде.

**Навіщо `restore()`:** конструктор створює **новий** об'єкт (новий Id, статус `DRAFT`), а `restore()` **відновлює** збережений з файлу.

## 6. Два контексти: чому «товар» різний

- У **Catalog** `Product` — товар на вітрині з **поточною** ціною.
- В **Ordering** `OrderLine` — «фото» товару **на момент додавання**: своя копія назви й ціни.
- Тому Ordering **не використовує** клас `Product`. Це як `Customer` у Billing і Marketing у методичці (рис. 5).

**Як вони спілкуються:**

```text
OrderService ──► ProductCatalog (інтерфейс в Ordering, "мовою Ordering")
                      ▲ реалізує
              CatalogProductAdapter (Infrastructure) ──► CatalogService.get(id) (Catalog)
                      перекладає ProductDto → CatalogProduct
```

- Класи `ordering` не імпортують класи `catalog` і навпаки (це перевіряють `Checks`).
- **Видалили товар** → старі замовлення не змінюються (там своя копія), а в нове замовлення додати його не можна → 404.
- «Зовнішнього ключа» між контекстами немає — кожен володіє своїми даними.
- Контексту покупців (Customer Management) **немає**: тільки `CustomerId` без перевірки, щоб не ускладнювати.

## 7. Як працює запит — сценарій «додати товар»

```text
POST /orders/{id}/items  {"productId":"...","quantity":2}
 ▼ WebApi      OrderEndpoints — розбирає JSON, викликає сервіс (правил тут немає!)
 ▼ Application OrderService.addItem:
 │   1) store.findById(orderId)        → OrderStore → FileOrderStore
 │   2) catalog.findProduct(productId) → ProductCatalog → CatalogProductAdapter → CatalogService
 │   3) order.addItem(...)             → Domain перевіряє правила (або DomainRuleException)
 │   4) store.update(order)            → збереження + перевірка версії
 │   5) toDto(order)
 ▼ WebApi      Router: DTO → JSON 200; помилки → 400 / 404 / 409 …
```

**Помилки → HTTP-коди (усе в `Router`):**

| Що сталось | Код |
|---|---|
| Порушено бізнес-правило (`DomainRuleException`) | 400 |
| Кривий JSON / Id (`BadRequestException`) | 400 |
| Не знайдено (`NotFoundException`) | 404 |
| Не той метод | 405 |
| Хтось змінив замовлення одночасно (`ConcurrentChangeException`) | 409 |
| Тіло > 16 КБ | 413 |
| POST без `Content-Type: application/json` | 415 |
| Непередбачена помилка | 500 (без подробиць для клієнта) |

## 8. Ключові рішення — і чому саме так

| Рішення | Чому |
|---|---|
| Шари = окремі модулі Maven | Як окремі `.csproj` у прикладі на C#; неправильну залежність не дасть зробити компілятор |
| Domain без залежностей | Вимога методички; правила можна перевірити без HTTP і файлів |
| Інтерфейси сховищ в Application | Сценарії не знають, де лежать дані; заміна файлів на БД зачепить тільки Infrastructure |
| Правила в конструкторах Value Objects | Неправильний об'єкт не створиш; немає дублювання перевірок |
| Перевірки до зміни стану | Відмова не залишає «напівзмінене» замовлення |
| Контракт `ProductCatalog` з боку Ordering | Ordering не залежить від моделі Catalog |
| `version` + 409 | Оптимістичне блокування: два одночасні запити не затруть один одного |
| Файли замість SQLite | Умова — чиста Java без бібліотек; драйвер БД був би сторонньою бібліотекою |
| Свій `Json` + `HttpServer` з JDK | Та сама причина; це деталі WebApi, Domain про них не знає |
| DI вручну в `InternetShopApp` | Немає фреймворку; одне місце, де видно всі підстановки |

**C# → Java (коротко):** `.slnx` → батьківський `pom.xml`; `.csproj` → модулі Maven; `record CourseTitle` → `record ProductName`/`Money`/…;
`Course + Enrollment` → `Order + OrderLine`; `ICourseStore` → `ProductStore`/`OrderStore`; EF Core + SQLite → файли; `Program.cs` → `InternetShopApp` + `Router`;
`CourseDemo.Checks` → `internetshop-checks`.

**Безпека (якщо спитають):** сервер слухає лише localhost; клієнт не бачить стек помилок; POST тільки з JSON (захист від CSRF);
ліміти 16 КБ і глибина JSON 20; екранування `< > &` і `textContent` на сторінці (від XSS); заголовки CSP, `X-Frame-Options`, `nosniff`; `data/` і `target/` не в Git.

## 10. Що показати на захисті (≈ 3–4 хв)

1. **Дерево проєкту:** 4 модулі-шари; у Domain і Application — пакети `catalog` і `ordering`.
2. **`internetshop-domain/pom.xml`:** розділу `<dependencies>` немає → Domain ні від чого не залежить. Для порівняння — `internetshop-application/pom.xml` (тільки domain).
3. **`Order.java`:** `addItem`, `place`, `ensureDraft`, `getLines()` лише для читання — «ось тут живуть правила».
4. **`InternetShopApp.java`:** «ось де інтерфейси отримують реалізації».
5. **Сторінка http://localhost:8080:**
   - «Створити замовлення» → додати 2 шт. → видно суму;
   - ввести 120 → червоне повідомлення `HTTP 400: Кількість одного товару має бути від 1 до 99.` (текст правила з Domain);
   - «Оформити» → статус `PLACED`;
   - спробувати додати ще → `Замовлення вже оформлене, змінювати його не можна.`
6. **Видалити товар** кнопкою «Видалити» → зник з каталогу, а в старому замовленні рядок лишився (bounded contexts незалежні).
7. **Перезапустити** застосунок → замовлення на місці (файли в `data/`).
8. **Maven → verify** → `All 51 checks passed.` і `BUILD SUCCESS`.

Альтернатива п. 5–6: `./demo.ps1 -StepByStep` — 11 кроків, включно з 404 для неіснуючого товару.

## 12. Контрольні питання з методички — короткі відповіді

**Основна ідея чистої архітектури?**
Бізнес-логіка в центрі й не залежить від фреймворків, БД, UI. Залежності тільки всередину. У нас: WebApi/Infrastructure → Application → Domain, Domain — ні від чого. Можна замінити сховище, змінивши лише Infrastructure.

**Що таке DDD і його роль?**
Проєктування навколо моделі предметної області з єдиною мовою бізнесу й коду. Визначає, що в центрі (Domain) і де межі частин (bounded contexts). У нас: Entity, Value Objects, агрегат `Order`, контексти Catalog і Ordering.

**Призначення bounded context?**
Межа, де модель і слова однозначні; не робимо одну «універсальну» модель. У нас «товар» у Catalog має поточну ціну, а в Ordering ціна зафіксована при додаванні. Спілкування — через `ProductCatalog`.

**Які залежності дозволені між шарами?**
Тільки всередину: Application → Domain; Infrastructure → Application, Domain; WebApi → Application, Infrastructure, Domain. Domain — ні від чого. Задано в `pom.xml`, перевіряється в `Checks`.

**Чому домен ізольований від інфраструктури?**
Правила стабільніші за технології. Домен можна перевірити без БД і HTTP (так і роблять `Checks`), а зміна сховища не чіпає правил. Інакше логіка розповзається по контролерах (рис. 2–3 методички).

## 13. Імовірні додаткові питання

> Це моє припущення на основі методички та коду, а не список від викладача.

- **Entity vs Value Object?** Entity має Id і може змінюватись (`Order` змінює статус). VO — лише значення, незмінний: `Money("10")` дорівнює `Money("10.00")`.
- **Чому `OrderLine` — Entity, а не VO?** Має Id і змінюваний стан (кількість росте при повторному додаванні), але живе тільки всередині `Order`.
- **Чому `Order` — корінь агрегату?** Правила «≤ 99» і «лише DRAFT» стосуються всього замовлення, тож усі зміни йдуть через нього.
- **Чи є бізнес-логіка в контролерах?** Ні. Ендпоінти лише розбирають запит і викликають сервіс. Навіть текст помилки формує Domain.
- **Де логіка видалення товару?** `CatalogService.delete`: перевірка, що товар є → `ProductStore.remove`. Ендпоінт лише повертає 204.
- **Два користувачі змінюють замовлення одночасно?** У `Order` є `version`; `FileOrderStore.update` порівнює версію → другий отримає 409.
- **Як перейти на справжню БД?** Додати в Infrastructure нові `OrderStore`/`ProductStore` і змінити 2 рядки в `InternetShopApp`. Domain і Application не змінюються.
- **Чому без Spring?** Умова — чиста Java без бібліотек. Maven — лише інструмент збірки (модулі + напрям залежностей + запуск перевірок).
- **Як зберігаються дані?** Текстові файли `data/*.db`; текстові поля в Base64; запис через тимчасовий файл і заміну (атомарно); у файл пишуться записи (`ProductRecord`, `OrderRecord`), а доменні об'єкти відновлюються через `restore()`.
- **Чим відрізняється від прикладу CourseDemo?** Java замість C#, два контексти замість одного, файли замість SQLite, Maven-модулі замість `.csproj`.

## 14. Чого в проєкті НЕМАЄ (щоб не сказати зайвого)

- автентифікації, кошика, оплати, складських залишків, скасування замовлення, редагування товарів;
- контексту Customer Management — лише `CustomerId`;
- бази даних і міграцій — лише файли;
- Domain Events і DI-контейнера;
- фільтрації замовлень за покупцем: `GET /orders` повертає всі (для навчального демо це прийнятно).
