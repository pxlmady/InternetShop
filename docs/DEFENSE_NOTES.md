# Підготовка до захисту — ПР №1 (InternetShop, Clean Architecture + DDD)

> Робочий конспект для себе, а не формальна документація. Формальний опис — у [README.md](../README.md).

## 1. Що зроблено — коротко (30 секунд)

- Предметна область — **інтернет-магазин**.
- Багатомодульний проєкт **Maven** на **чистій Java 21** (IntelliJ IDEA) поділено на 4 шари-модулі: **Domain → Application → Infrastructure → WebApi**, плюс модуль перевірок.
- Виділено два **bounded context**:
  - **Catalog** — товари;
  - **Ordering** — замовлення.
- Ordering отримує дані з Catalog лише через контракт `ProductCatalog`, який реалізує адаптер.
- Бізнес-правила живуть **тільки в Domain**: у Value Objects і в корені агрегату `Order`.
- Застосунок запускається на <http://localhost:8080>, дані зберігаються у файлах і переживають перезапуск.
- 51 консольна перевірка покриває правила, збереження, межі шарів і контекстів та HTTP.

## 2. Карта проєкту — що де лежить

| Шукаю… | Де |
|---|---|
| Бізнес-правила замовлення | `internetshop-domain/.../domain/ordering/Order.java` |
| Value Objects | `ProductName`, `Quantity`, `CustomerId` (у своїх контекстах), `Money` (у `domain/shared`) |
| Сценарії (use cases) | `application/catalog/CatalogService.java`, `application/ordering/OrderService.java` |
| Контракти (інтерфейси) | `ProductStore`, `OrderStore`, `ProductCatalog` в Application |
| Реалізації контрактів | `infrastructure/persistence/File*Store.java`, `infrastructure/integration/CatalogProductAdapter.java` |
| Де все з'єднується | `webapi/InternetShopApp.java` (Composition Root) |
| Обробка помилок → HTTP-статуси | `webapi/http/Router.java` (метод `handle`) |
| HTTP-маршрути | `webapi/endpoints/ProductEndpoints.java`, `OrderEndpoints.java` |
| Залежності між шарами | `pom.xml` кожного модуля, розділ `<dependencies>` |
| Перелік модулів, версія Java | кореневий `pom.xml` |
| Перевірки | `internetshop-checks/.../Checks.java` |

**Порядок читання коду** (як радить README CourseDemo): `Order` → `OrderLine`, `Quantity`, `Money` → `OrderService`, `OrderStore`, `ProductCatalog` →
`FileOrderStore`, `CatalogProductAdapter` → `InternetShopApp` → `Router`.

## 3. DDD у проєкті — де саме

| Поняття DDD | Що це простими словами | Де в проєкті |
|---|---|---|
| **Entity** (сутність) | Об'єкт з ідентичністю: однаковий Id означає той самий об'єкт, навіть якщо дані змінились | `Product`, `Order`, `OrderLine` (базовий клас `Entity`, `equals` за Id) |
| **Value Object** | Об'єкт без ідентичності: важливе лише значення; незмінний і перевірений при створенні | `Money`, `ProductName`, `Quantity`, `CustomerId` — Java `record` |
| **Aggregate** (агрегат) | Група об'єктів, що змінюється як одне ціле | `Order` + його `OrderLine` |
| **Aggregate Root** | Єдина «вхідна двері» агрегату, яка захищає правила | `Order`: `addItem`, `place`; рядки змінити напряму неможливо |
| **Інваріант** | Правило, що має залишатися істинним після будь-якої операції | ≤ 99 шт. товару, зміни лише у `DRAFT`, не оформлювати порожнє |
| **Bounded Context** | Межа, в якій модель і терміни мають одне значення | `catalog` і `ordering` — окремі пакети в Domain та Application |
| **Repository** (тут Store) | Колекція агрегатів; приховує, як вони зберігаються | `ProductStore`, `OrderStore` (інтерфейси) → `File*Store` |
| **Application Service** | Організовує сценарій, але не приймає бізнес-рішень | `CatalogService`, `OrderService` |
| **Anti-Corruption Layer** | Перекладач між моделями різних контекстів | `CatalogProductAdapter` |
| **Shared Kernel** | Невелика спільна частина моделі для кількох контекстів | `Money`, `Entity`, `DomainRuleException` у `domain.shared` |
| **Ubiquitous Language** | Однакові терміни в розмові та в коді | `Order.place()`, `addItem`, `DRAFT`/`PLACED`, `Quantity` |

### Чому «товар» у двох контекстах різний

- У **Catalog** `Product` — позиція вітрини: назва, опис, поточна ціна.
- В **Ordering** — `OrderLine`: «знімок» назви й ціни **на момент додавання**. Якщо ціна в каталозі зміниться, вже сформоване замовлення не зміниться.
- Це те саме, що `Customer` у Billing і Marketing з методички (рис. 5).

## 4. Як частини взаємодіють — сценарій «додати товар»

```text
POST /orders/{id}/items  {"productId": "...", "quantity": 2}
 │
 ▼  WebApi — OrderEndpoints: розбирає JSON, викликає сервіс (правил немає)
 ▼  Application — OrderService.addItem:
 │     1) store.findById(orderId)         → OrderStore (інтерфейс) → FileOrderStore
 │     2) catalog.findProduct(productId)  → ProductCatalog (інтерфейс) → CatalogProductAdapter → CatalogService (Catalog)
 │     3) order.addItem(...)              → Domain перевіряє правила; при порушенні DomainRuleException
 │     4) store.update(order)             → збереження з перевіркою версії
 │     5) toDto(order)
 ▼  WebApi — Router: DTO → JSON 200; DomainRuleException → 400; NotFound → 404; ConcurrentChange → 409
```

Важливо пояснити: **порядок виклику** (WebApi → Application → Infrastructure) не збігається з **напрямом залежностей коду**.
Application викликає сховище через **свій** інтерфейс, тож залежність спрямована всередину: Infrastructure → Application.

## 5. Ключові рішення і чому саме так

| Рішення | Чому |
|---|---|
| Шари як окремі модулі Maven | Як окремі проєкти `.csproj` у CourseDemo. Модуль не може використати те, від чого не залежить у своєму `pom.xml`, тому правило залежностей перевіряє компілятор, а не домовленість |
| Domain без жодних залежностей | Вимога методички: доменна модель не залежить від фреймворків та інфраструктури, її можна перевірити без HTTP і файлів |
| Інтерфейси сховищ в Application | Інверсія залежностей: сценарії не знають, де зберігаються дані; заміна файлів на БД зачепить лише Infrastructure |
| Правила в конструкторах Value Objects | Некоректний об'єкт неможливо створити, тож перевірка не дублюється по коду |
| Перевірка перед зміною стану | Відхилена операція не залишає агрегат у «напівзміненому» стані |
| Контракт `ProductCatalog` з боку Ordering | Ordering описує, що йому потрібно, своєю мовою; від моделі Catalog він не залежить |
| `version` і HTTP 409 | Два одночасні запити не перезапишуть зміни один одного (оптимістичне блокування) |
| Файлове сховище замість SQLite | Умова — чиста Java без бібліотек; драйвер БД був би сторонньою бібліотекою. Завдяки контракту це деталь Infrastructure |
| Власний мінімальний `Json` і `HttpServer` з JDK | Та сама причина. Це технічні деталі WebApi; Domain і Application про JSON/HTTP не знають |
| DI вручну в `InternetShopApp` | Немає фреймворку; одне місце, де видно, яка реалізація підставляється під кожен інтерфейс |
| Немає Customer-контексту, лише `CustomerId` | Як `StudentId` у CourseDemo: функціонал не ускладнюємо, а межу контексту показуємо |

## 6. Запуск і демонстрація на захисті

**Перший раз:** IntelliJ → File → Open → папка `InternetShop` → Open as Project (Maven імпортує 5 модулів).

**Запуск:** IntelliJ → конфігурація **InternetShop (localhost:8080)** → Run → <http://localhost:8080>.
Без IntelliJ: `mvn package`, потім `java -jar internetshop-webapi/target/internetshop.jar` (або `./run.ps1`).

**План демонстрації (≈ 3 хв):**
1. Показати дерево проєкту: 4 модулі-шари, у Domain і Application пакети `catalog` та `ordering`.
2. Відкрити `internetshop-domain/pom.xml`: розділу `<dependencies>` немає взагалі, лише JDK. Для порівняння — `internetshop-application/pom.xml` залежить тільки від domain.
3. Відкрити `Order.java`: методи `addItem`, `place`, `ensureDraft`, а `getLines()` повертає незмінну колекцію.
4. На сторінці <http://localhost:8080>:
   - створити замовлення → додати 2 шт. товару;
   - ввести кількість 120 → з'явиться помилка 400 з текстом правила з Domain;
   - натиснути «Оформити» → статус `PLACED`;
   - спробувати додати ще → помилка 400 «Замовлення вже оформлене».
5. Альтернатива п. 4 — у другому терміналі виконати `./demo.ps1 -StepByStep`: усі сценарії по кроках, включно з 404 для неіснуючого товару.
6. Зупинити й знову запустити застосунок → замовлення на місці (файли в `data/`).
7. Видалити товар з каталогу кнопкою «Видалити»: він зникне з каталогу, а в уже створених замовленнях рядок із ним залишиться.
8. Maven → Lifecycle → **verify** (або `mvn verify`) → `All 51 checks passed.` і `BUILD SUCCESS`.

## 7. Контрольні питання з методички — короткі відповіді

**У чому основна ідея чистої архітектури?**
Бізнес-логіка в центрі й не залежить від зовнішніх деталей: фреймворків, БД, UI. Залежності спрямовані лише всередину:
WebApi та Infrastructure залежать від Application, Application — від Domain, Domain — ні від чого.
У проєкті сховище можна замінити, змінивши тільки Infrastructure.

**Що таке DDD і яка його роль в архітектурі?**
Це підхід, за якого архітектура будується навколо моделі предметної області. Модель відображає бізнес-процеси і використовує спільну з бізнесом мову.
Роль DDD: визначити, *що* лежить у центрі (Domain) і де проходять межі між частинами системи (bounded contexts).
Приклади в проєкті: сутності, Value Objects, агрегат `Order` з інваріантами, контексти Catalog і Ordering.

**Яке призначення bounded context?**
Він задає межу, в якій модель і терміни однозначні. Так уникаємо однієї «універсальної» моделі з несумісними відповідальностями.
Приклад: «товар» у Catalog має поточну ціну, а в Ordering ціна фіксується на момент додавання. Контексти спілкуються лише через контракт `ProductCatalog`.

**Які залежності дозволені між шарами?**
Лише всередину: Application → Domain; Infrastructure → Application (і Domain); WebApi → Application, Infrastructure (і Domain, для типів помилок).
Domain ні від чого не залежить. Зворотні залежності заборонені. У проєкті це задано в `pom.xml` модулів і перевіряється в `Checks`.

**Чому доменна модель має бути ізольованою від інфраструктури?**
Бізнес-правила стабільніші за технології. Ізольовану модель можна перевірити без БД і HTTP (так і зроблено в `Checks`),
а зміна сховища чи фреймворку не вимагає переписувати правила. Інакше бізнес-логіка розповзається по контролерах і SQL (рис. 2–3 методички).

## 8. Ймовірні додаткові питання

> Ці питання — моє припущення на основі матеріалів і коду, а не перелік від викладача.

- **Чим Entity відрізняється від Value Object?** Entity має ідентичність (Id) і може змінюватися (`Order` змінює статус).
  Value Object визначається значенням і незмінний: `Money("10") == Money("10.00")`.
- **Чому `OrderLine` — сутність, а не Value Object?** Вона має Id і змінюваний стан (кількість збільшується при повторному додаванні),
  але існує лише всередині агрегату `Order` (як `Enrollment` у CourseDemo).
- **Чому `Order` — корінь агрегату?** Правила «≤ 99 шт.» і «лише в DRAFT» стосуються всього замовлення, тому зміни йдуть тільки через нього.
- **Де бізнес-логіка в контролерах?** Її там немає: ендпоінти лише розбирають запит і викликають сервіс. Навіть повідомлення про помилки формує Domain.
- **Навіщо `restore`, якщо є конструктор?** Конструктор створює новий об'єкт (новий Id, статус `DRAFT`), а `restore` — відновлює збережений.
  Під час відновлення правила Value Objects і рядків теж перевіряються.
- **Що станеться із замовленнями, якщо видалити товар з каталогу?** Нічого: `OrderLine` зберігає власну копію назви й ціни (модель Ordering).
  Новий товар з таким Id додати вже не можна, бо `ProductCatalog` його не знайде, і API поверне 404.
  Так bounded contexts залишаються незалежними: між ними немає зовнішнього ключа, лише контракт (див. перевірку «Existing order keeps its snapshot after product deletion»).
- **Де логіка видалення?** У сценарії `CatalogService.delete` (перевірка наявності → `ProductStore.remove`). Ендпоінт лише викликає сервіс і повертає 204.
- **Що буде, якщо два користувачі одночасно змінять замовлення?** Другий отримає HTTP 409 завдяки перевірці `version` у `FileOrderStore.update`.
  Перевірка «Concurrent update rejected» у `Checks` імітує саме це.
- **Як перейти на справжню БД?** Додати в Infrastructure нову реалізацію `OrderStore`/`ProductStore` і змінити два рядки в `InternetShopApp`.
  Domain і Application не змінюються.
- **Чому немає Spring?** Умова — чиста Java без сторонніх бібліотек. Maven використано лише як інструмент збірки: модулі-шари й залежності між ними, жодних зовнішніх залежностей. Складання об'єктів (DI) виконується вручну в Composition Root.
- **Навіщо Maven, якщо бібліотек немає?** Він задає модулі та напрям залежностей між шарами (аналог `.csproj`), однаково збирає проєкт в IntelliJ і з командного рядка та запускає перевірки (`mvn verify`).
- **Чим відрізняється від CourseDemo?** Мова (Java), два контексти замість одного, файлове сховище замість SQLite, збереження агрегату через `add`/`update` замість `Add` + `Save`.
  Таблиця відповідностей є в README.

## 9. Чого в проєкті НЕМАЄ (щоб не сказати зайвого)

- Немає автентифікації, кошика, оплати, складських залишків, скасування замовлення, редагування товарів. Видалення товару є, але лише «жорстке» (без архіву чи відновлення).
- Немає контексту Customer Management: є лише `CustomerId` без перевірки існування покупця.
- Немає БД і міграцій: дані зберігаються у файлах `data/*.db` (текстовий формат, не SQLite).
- Немає доменних подій (Domain Events) і DI-контейнера.
- `GET /orders` повертає всі замовлення всіх покупців. Для навчального демо це прийнятно, але в реальному магазині потрібні автентифікація й фільтрація.
